# 三个仓库能不能合并成一个项目？

> 结论先行：**仓库能合，安装能不能变成"一次"取决于是否把后端搬进浏览器。**
> 在 TT酒馆（TauriTavern）上这不是权衡——它没有 Node 服务端，服务端插件根本不会运行；
> 所以"一次安装"的唯一正解是前端化后端，而不是把三个 git 仓库塞进一个文件夹。
> 本目录（`rp-hub-unified/`）就是按这个判断做出来的可运行原型。

---

## 一、先看清三个部件到底是什么运行时

| 部件 | 运行时 | 怎么被加载 | 对别人的依赖 | 证据 |
| --- | --- | --- | --- | --- |
| **Backend** | Node（ESM 插件） | 放在 `<ST>/plugins/`，且 `config.yaml` 里 `enableServerPlugins: true`；ST 启动时 `init(router)` 并 `app.use('/api/plugins/<info.id>', router)` | 无（自包含），但**只能在有 Node 的 ST 里跑** | ST `src/plugin-loader.js`：`getConfigValue('enableServerPlugins', false)`；`app.use(\`/api/plugins/${id}\`, router)` |
| **RegexPlus** | 酒馆页面（前端 ESM 扩展） | `manifest.json` 的 `hooks.activate → init`，**纯 ESM 无构建** | 对后端是**软依赖**：`GET /cards/by-name/:name` 判模式，失败即降级 `st` | `src/store/rp-mode.js:283`（by-name）、`:288`（marks 兜底）、`:304-333`（三条降级路径） |
| **RP助手** | 酒馆助手（JS-Slash-Runner）脚本 iframe | webpack 产物，挂 `#extensions_settings2` | 对后端是**硬依赖形状**：导入分流、模板列表、变量视图、marks | `导入拦截.ts:313/339`、`模型解析服务.ts:256-300`、`TabVariables.vue:1021-1026`、`楼层变量服务.ts:137`、`模板渲染服务.ts:614-620` |

三条硬事实：

1. **三者不是一个应用的三层，而是三个宿主**：Node 进程 / 酒馆页面 / 酒馆助手 iframe。
   合并仓库只解决"源码和版本"，不改变宿主数量。
2. **TT酒馆没有服务端插件这回事**。TauriTavern 官方扩展文档原话：
   "Node server plugins cannot run, because there is no SillyTavern server."
   同一份文档还说明扩展的 served path 是 `/scripts/extensions/third-party/<folder>/`，
   与 SillyTavern 一致 —— 这正好是前端化方案能复用的一切。
3. **`src/` 的位置是不可动的**：`src/st-bridge.js:33` 用
   `from '../../../../../script.js'`（5 层上溯到 `public/script.js`）。
   所以 RegexPlus 必须待在 `third-party/<dir>/src/…`，不能塞进 `packages/regex-engine/`。
   这一条直接决定了合并后的目录形态（`src/` 留根，见下）。

## 二、四条路线，选哪条

| | A. 三仓不动 + 安装器 | B. 单仓双产物 | C. 单仓 + 后端前端化（**已落地**） | D. Service Worker 拦截 |
| --- | --- | --- | --- | --- |
| TT酒馆可用 | ✗（无插件 → RP 卡不可用） | ✗ | ✓（全部走浏览器） | ✓ |
| 桌面 ST 功能 | ✓ 全量 | ✓ 全量 | ✓ 全量（插件变成可选增强） | ✓ |
| 安装步数 | 扩展 1 次 + 脚本 1 次 + 改 config + 重启 | 同 A | **扩展 1 次**（想用服务器库再加 1 次可选脚本） | 1 次（但要单独注册 SW） |
| 版本一致性 | 三处版本号，易漂 | 一处 | 一处 | 一处 |
| 维护成本 | 低 | 中 | 中高（双实现，需对拍闸门） | 高（SW 生命周期/缓存坑多） |
| 主要风险 | 用户装不明白 | 仍装不明白 | 双实现漂移、本地库不跨设备 | 作用域与更新极难调试 |

**A** 只是把"文档里三步"写成脚本，没有解决 TT酒馆；**B** 是工程的正确姿势但体验不变；
**D** 技术上可行（SW 能拦 `/api/plugins/...`），但 SW 注册、更新、scope 与酒馆的 iframe 生态
冲突面太大，且仍要在每个 realm 里装东西，**收益不如直接 patch `fetch`**，故弃。

选 **C**：仓库合并 + 把 `server/lib` 的解析归一搬进浏览器 + 用 fetch 拦截保持调用点零改动。
服务端插件不删除，降级为"想在多设备间共享卡库时的可选增强"。

## 三、推荐形态（原型已按此搭建）

```
rp-hub-unified/                 ← 一个 git 仓库 = 一个可安装扩展
├─ manifest.json                扩展清单（只有这一份）
├─ index.js                     init：装本地后端 → 引擎管道 → 注册面板脚本
├─ src/                         RegexPlus 原样（硬约束：5 级相对 import）
├─ local/                       ★ 后端逻辑的浏览器实现（17 文件 / 1651 行）
├─ panel/                       ★ 面板桥（enabler/注册/写回/上游产物）
├─ server/                      Node 插件原样（可选增强）
└─ tools/                       install-server.*、fetch-panel、fidelity-test、api-test
```

### 四个关键设计

1. **零改动接管接口**
   两个前端都是 `BASE = origin + '/api/plugins/rp-hub-compat/v1'` 再 `fetch(BASE + path)`
   （RP助手产物里该基址出现 14 次）。`local/fetch-shim.js` 只包一层 `window.fetch`，
   命中前缀转 `local/api.js`，**30+ 处调用点一行不改**。
   `auto` 模式先探 `GET /status`：真插件在 → 直连服务器库；不在 → 本地 IndexedDB。

2. **跨 realm 也要装一次**
   iframe 有独立 `fetch`，父窗口的 patch 不生效。所以 `panel/enabler.js` 在酒馆助手 iframe 里
   再 `installLocalBackend()` 一次；两份 shim 共用同一个 IndexedDB（同源）。
   这也解释了为什么"合并仓库"在这里是必要的：面板脚本和扩展必须引用**同一份** `local/`。

3. **逐位一致，而不是"差不多"**
   自写同步 SHA-256（`local/sha256.js`，`crypto.subtle` 在局域网 http 下不可用），
   于是 `contentHash`、`stableId`、`cardId` 与 Node 版完全相同 —— 同一张卡在两种模式下
   是同一个对象，marks 键也对得上。PNG 的 zTXt/iTXt 用 `DecompressionStream('deflate')` 解压。

4. **写回改道**
   服务端 `upload?writeBack=1` 会重新生成标准卡 PNG；浏览器不做 PNG 编码，直接调
   ST 自己的 `POST /api/characters/import`（`panel/st-import.js`），世界书/正则询问弹窗
   行为与原生拖入一致。

### 3.5 动手前的复查：这一轮先修掉的 6 处

“先把原型跑通”之后、把 TT 适配落下之前，把代码重新当别人的代码读了一遍。发现的问题与处置：

| # | 问题（为什么是问题） | 处置 |
| --- | --- | --- |
| 1 | **卡库没分表**：`cards` 一条记录同时装 `normalized + raw(blocks)`，而 `readIndex()` 走 `getAll()` —— 于是 `by-name` / `exists` / `status` 这些高频轻量查询被大卡正文拖成 O(卡体总量)，几张 MB 级卡就能把每次切角色都卡住 | `DB_VERSION=2` 拆成 `cards`（元数据）/`payload`（卡体）/`marks`；`readIndex`/`findByName`/`stats` 只碰元数据表，`stats` 改 `count()` |
| 2 | **面板产物被下载两次**：`enabler` 先 `GET` 检查再 `import`，236 KB 走两遍 | 改 `HEAD` 探测 + 直接 `import` |
| 3 | **导入通道单一**：本地模式写回只依赖 `/api/characters/import`，纯前端宿主（TT）未必有该路由 | 两条通道：ST 原生接口 → `TavernHelper.importRawCharacter`，都失败才报错（卡已在本地库） |
| 4 | **PNG 解压一次性翻倍占用**：`new Blob([payload])` + `arrayBuffer()` 对大 zTXt 块是 2~3 份内存 | 改流式 `reader` 循环 + 边读边校验 16 MB 上限，超限 `cancel()` |
| 5 | **入口太“脆”**：`index.js` 静态拉起整张模块图，`/script.js` 缺失时求值阶段就死，用户只看到一句 “Failed to fetch dynamically imported module” | 入口变薄：只装本地后端，再动态 `import('./boot.js')`；失败时按错误特征给出**可执行指引**（含 `fetch('/script.js')` 自检命令 + 换 TT 版） |
| 6 | **没有可自证的诊断面**：真机排查全靠猜 | 新增 `local/compat.js`：`probeEnvironment()`（10 项布尔）+ `checkCoreScript()`；挂到 `window.__rphub__` |

### 3.6 为什么 TT 适配是「构建期变体」而不是运行时兜底

第一反应是让 `st-bridge.js` 用顶层 `await import()` 试 ST 路径、失败再落适配器。**这条路走不通**，原因在语义而不在语法：

- ST 的 `script.js` 导出的是**活绑定**（`this_chid`、`characters` 随切角色变化）。用
  `const { this_chid } = mod` 取到的是快照，切卡后引擎仍然按旧 id 取正则与卡数据 —— 静默错，且很难查。
- 顶层 await 只能解决“模块能不能加载”，解决不了“绑定是不是活的”。

所以采用构建期换文件：`variants/tt/st-bridge.js` 用 `export let` + 事件/1s 轮询把
`SillyTavern.getContext()` 的最新值刷进同一条绑定（导入方看到的仍是会变的值），
其余 21 个导出保持同名同义。代价是两套产物，收益是两种宿主都不用牺牲正确性。

补记（第二处依赖，做完 st-bridge 才发现）：`src/panel/ui.js` 为了复刻酒馆原版正则设置面板，
直接 import 了 **8 个**酒馆内部模块（`script.js`/`utils.js`/`templates.js`/`popup.js`/
`AccountStorage.js`/`i18n.js`/`extensions.js`/`preset-manager.js`/`group-chats.js`），
`src/store/scripts.js` 还从 `utils.js` 取 `uuidv4`。只换 st-bridge 仍会在 TT 上 404。
TT 变体现在做三处替换，并由 `build-variant.mjs` 跑**硬校验**——产物里任何
`from '(\.\./){4,}…'` 都判失败（当前 `externalImports: 0`）。

发布路径也按 TT 的实际契约收敛：TT 支持匿名 http(s) git + 指定分支，**不支持 ZIP**，
所以 `tools/publish-tt-branch.ps1` 把 `dist/tt` 推成孤儿分支 `tt`，用户在扩展里填同一个
URL + Branch=tt 即可——仍然是“一条 git URL 安装”，不是让用户去解压文件夹。

## 四、验证（可复现，不是"应该能跑"）

```bash
node tools/fidelity-test.mjs    #  8 项：与 server/lib 对拍
node tools/api-test.mjs         # 28 项：接口契约
node tools/shim-test.mjs        # 10 项：fetch 拦截层
node tools/store-test.mjs       # 17 项：卡库分表 / 导出导入
# 合计 63 项断言，全部通过
```

对拍覆盖：真实 V3 卡（chara+ccv3 双块）、普通 ST 卡、合成 RP 卡（包裹/直出 JSON、
tEXt/zTXt/iTXt 三条 PNG 解码路径）。比较的是 `format/spec/formatDetail/features/normalized`
**逐字段相等**，含拼接出的 `stableId` 与 `sha256`。

接口覆盖：`analyze`（rphub 特征识别）、`upload?writeBack=1`（入本地库 + 交给原生导入）、
`status`、`by-name`（含 contentHash 精确匹配）、`variables?fields=uiTemplates`、`exists`、
`marks` PUT/GET/LIST/DELETE、`st` 视图明确 501、普通卡 `formatDetail=st` 让位、
422/404/ROUTE_NOT_FOUND 错误码。

拦截层覆盖：`auto` 模式认出真插件后**不接管**（请求确实走网络层）、强制 `local` 后 base 前缀
请求就地接管（含 `ArrayBuffer` body 与 `X-Filename` 头、无 `Content-Type` 的 marks PUT）、
非 base 请求（`/api/characters/import`）原样透传。

## 六、代价与风险（明面写清）

1. **双实现漂移**：`server/lib` 与 `local/` 是同一套语义的两份实现。
   闸门是对拍脚本进 CI；长期更好的做法是让插件变薄壳（只做 Express 路由 + 文件系统 +
   ST 登录校验），解析/归一复用 `local/` 的纯函数，Node 侧注入 Buffer/fs 适配。
2. **数据分裂**：IndexedDB 库 ≠ 服务器库，marks 也各存一份。
   卡本身仍在 ST 角色目录，丢的只是归一缓存与标记；需要跨设备就去装插件，或后续做导出/导入。
3. **性能与容量**：大卡（MB 级 PNG、上千条正则）要在浏览器里解析；`normalized` 里含
   `raw.unmapped`，IndexedDB 可能吃到几十 MB。建议后续把 raw 视图改成按需存储。
   实测 84KB chara 块的解析在毫秒级，瓶颈在 IDB 写入而非解析。
4. **面板产物仍是上游 webpack**：本仓用 `tools/fetch-panel.mjs` 取 `dist/RP-HUB/index.js`
   （236 KB，基址 14 处，无 CDN 依赖）。要在本仓改面板 UI，得把面板工程搬进来接 CI。
5. **兼容性红线不变**：必须关闭原版正则插件（两套引擎同时跑会双重替换）；鸡尾酒需删
   `manifest.json` 里的原版正则依赖；Soliumbra 特殊兼容。
6. **`st` 视图未实现**：本地无 PNG 编码器，明确返回 `501 LOCAL_NOT_IMPLEMENTED`，
   不伪造成功。
7. **安全面**：服务器模式的 upload/marks 仍走 ST 的 `requireLoginMiddleware`；本地模式
   没有"别人的服务器"，但 IndexedDB 对同源脚本可见（与酒馆助手生态其它脚本同级）。

## 八、一句话

**合并不是目的，拿到"把后端搬进浏览器"的工程空间才是。** 合了仓之后，
RegexPlus、RP助手、本地后端才能引用同一份解析实现、同一个版本号、同一个 CI 闸门；
在 TT酒馆上，这也是唯一能让 RP 卡真正跑起来的形态。
